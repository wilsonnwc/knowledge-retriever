# Semantic Search & Chunking — Learning Record

This document exists because "semantic search" and "chunking" are terms that show up constantly in AI PM job descriptions. This is a working record of what these terms actually mean, a real tradeoff this project ran into, and how we resolved it — written so it can be recited accurately and specifically in an interview, not just gestured at.

---

## Core Concepts (plain-language definitions)

**Keyword search** (what this project currently uses)
Matches literal words. Query "affordances" only finds notes containing the word "affordances." No understanding of meaning or synonyms.

**Semantic search**
Matches *meaning*, not literal words. A query like "how do I stop users making mistakes" can retrieve a note about "error messages" or "human error" even though none of those exact words appear in the query. This works by comparing the query and each note as vectors (embeddings) in a shared mathematical space and finding the closest ones.

**Embeddings**
A numerical representation of text (a list of numbers, e.g. 1536 dimensions for OpenAI's `text-embedding-3-small`) such that texts with similar *meaning* end up as nearby points in that space. Generated by a separate embedding model, not by the chat model. Cheap and fast compared to LLM generation calls.

**Chunking**
Before you can embed a document, you have to decide what "one unit" of text is. You don't embed a whole 150-line file as a single vector — too much mixed content in one vector produces a blurry, unhelpful embedding (a phenomenon sometimes called "semantic dilution"). Instead, you split ("chunk") the document into smaller pieces and embed each piece separately. **Chunking strategy is the decision of how to split.**

**Vector database (e.g. Chroma, Pinecone, pgvector)**
Stores the embeddings and lets you run a "nearest neighbour" search: given a query's embedding, find the N closest chunk embeddings. That's the retrieval step in RAG (Retrieval-Augmented Generation).

## Common Chunking Strategies (the landscape)

1. **Fixed-size chunking** — split every N characters/tokens (e.g. every 500 tokens), often with overlap between chunks so context isn't cut mid-sentence. Simple, fast, but ignores document structure — can split a thought in half.

2. **Recursive/structural chunking** — split along natural document boundaries first (paragraphs, then sentences, then characters as a fallback) so chunks don't break mid-idea. More common in production RAG systems than pure fixed-size.

3. **Semantic chunking** — use an embedding model to detect where the *topic* actually shifts within a document, and split there rather than at an arbitrary character count. More expensive to compute, used when document structure is unclear or absent (e.g. transcripts).

4. **Hierarchical / "parent-child" chunking** — embed small, focused child chunks for accurate retrieval matching, but when a child chunk is retrieved, return its larger parent section (or the whole parent document) to the LLM for generation. This decouples "what gets matched" (small, precise) from "what gets used as context" (larger, coherent). This is the pattern most relevant to this project — see below.

## The Tradeoff We Hit In This Project

Early in this project, quotes and article excerpts were saved as individual files — one file per idea, scattered across topic folders. When importing "Design of Everyday Things," this produced 14 separate files spread across 5 folders.

That structure is actually *good* for embeddings: each file is small, focused, and about one idea — exactly what makes a clean, unambiguous vector.

But it's *bad* for how a human uses the knowledge base: it fragments a single author's unified argument into scattered trivia, making it impossible to cite "Design of Everyday Things" as a coherent source in an interview, and hard to maintain (14 files to update instead of 1).

So we consolidated back down to one file per source, organized internally with `## Section Headers` by theme. This is better for citation and maintenance — but if we naively embedded the *whole file* as one vector once we add semantic search, we'd be back to the semantic dilution problem: one vector trying to represent "affordances," "flow state," "checklists," and "resilience engineering" all at once, which produces a mediocre, unfocused embedding that won't precisely match any single query.

**This is the exact tension the "parent-child chunking" pattern exists to solve.**

---

## The Resolution: Decouple Citation Unit from Retrieval Unit

**Decision:** The *file* stays the citation/maintenance unit (one file per source, human-facing). The `##` *section* becomes the retrieval/embedding unit (machine-facing) once semantic search is built. These don't have to be the same thing.

**Structural rule adopted now (so no rework is needed later):**
- Every `## Section Header` inside a consolidated file must be **self-contained** — understandable without needing the section before it. No "as mentioned above."
- Each section is capped at roughly 40–60 lines. If a section naturally exceeds that, it may deserve its own file.

**Planned chunking approach when semantic search is implemented (Phase 5 of this project):**
1. Parse each note file's YAML frontmatter (source, type, tags, date) and body separately.
2. Split the body by `##` headers — each section becomes one chunk.
3. Embed each chunk individually (small, focused → accurate matching).
4. Attach the *parent file's* metadata (source, tags, date) to every chunk, so a retrieved chunk about "Swiss Cheese Model" still carries `source: Design of Everyday Things` even though it was matched independently of the rest of the file.
5. At generation time, optionally expand the retrieved chunk back out to include its parent file's title/intro line, so Claude has enough framing to answer well — this is the "child chunk for matching, parent context for generation" pattern.

This means: **no need to re-split files today.** The section-header discipline we're already applying is the exact preparation step semantic chunking needs later.

## Why This Matters for AI PM Interviews

This is a genuinely common real-world RAG problem, not a toy exercise: production teams constantly trade off between "clean citation-friendly documents" and "embedding-friendly small chunks," and the parent-child / hierarchical retrieval pattern (used by LangChain's `ParentDocumentRetriever`, LlamaIndex's hierarchical node parser, and similar tools in other frameworks) is the standard industry answer.

**Interview-ready framing:** "I ran into the classic chunking tradeoff firsthand: consolidating notes by source made them citable and maintainable, but a single embedding for a whole multi-topic file would dilute retrieval accuracy. I resolved it by decoupling the citation unit (the file) from the retrieval unit (the section) — small chunks get embedded for precise matching, but they inherit the parent document's metadata so context isn't lost. That's the same 'parent-child chunking' pattern used in production RAG frameworks like LangChain — I hit the problem naturally, before I knew the pattern already had a name."
